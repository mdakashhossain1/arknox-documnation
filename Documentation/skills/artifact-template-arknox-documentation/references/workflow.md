# Source-to-manual workflow

## Scope and evidence

Inspect project instructions, architecture, routes, views, validation, services, relations, configuration, and environment examples. Do not assume Laravel/Flutter or Quizs modules in another project. Use English output unless explicitly changed by the user. Latest fixed identity: Arknox and info@arknox.in.

Maintain a coverage matrix: screen, actions, fields, option choices, defaults/validation, data origin, downstream effects, source evidence, screenshot, and verification status. Include settings/environment and app flows, not only dashboard headings.

## Complete each applicable feature

- Reach the screen and identify required access.
- Explain create/add from empty form through save and verification; include a practical example where useful.
- List exact dropdown/radio choices. For dynamic choices identify the records supplying them and how to create a missing parent.
- Explain required/optional fields, limits, defaults, upload types/sizes, ordering, active state, and translations.
- Explain edit behavior and when changes appear: fetch, cache refresh, worker restart, or app rebuild.
- Cover search/filter/reset/pagination, statuses, empty states, and validation/errors.
- Record exact delete/reset/upgrade popup text and button labels; explain Cancel, confirmation, dependency impact, and success/error verification. Observe and cancel destructive dialogs; documentation does not authorize deleting data.
- For notifications explain all audiences, recipients, destinations, conditional selectors, identifiers, prerequisites, and sent/delivered/read distinctions.
- For analytics explain each metric's numerator/denominator, source records, date scope, filters, hover/zoom/legend/export, empty data, and where underlying values can change. Do not describe static promotional labels as real monitoring.
- For settings document each screen/field and corresponding environment variable, UI-versus-env precedence, blank-secret handling, refresh/restart requirements, app effects, and rollback. Never copy real secrets.
- For apps explain text/data origins and distinguish content updates from code/native changes.
- Explain exported report content and actual download steps.

Distinguish implemented, observed, and unverified behavior. Do not invent features or copy Quizs scoring, user roles, accounts, customer identity, legal identifiers, or deployment domains.

## Screenshots

Prefer isolated local data. Capture readable form parts, dropdowns, detail pages, charts, and safely cancelled popups. Keep secrets and personal data out. Do not send external notifications/email simply to collect evidence. Browser demos cannot establish native provider behavior. Label setup diagrams illustrative.

Keep final images under Documentation. Temporary preview databases, app builds, servers, dependencies, and caches are not deliverables. Do not delete unrelated existing project assets without user authorization. The old .documentation-preview environment is not needed to use this template.

Overlay vector arrows and numbered legends using the content schema. Do not fabricate screens or alter screenshot values.

## Assembly and QA

Write structured content first; preserve brand geometry and typography. Adapt chapter count/order to the target project. Generate full PDF, chapters, renders, and reader from one source. Never hardcode 91 pages or 35 chapters.

Run the verifier. Inspect cover, contents, table continuations, numbered steps, screenshots, headers/footers, and conclusion visually. Text-bound checks do not detect every cell clipping defect. Verify complete steps, valid metadata, correct page totals/chapter starts, real images, and no blank pages.

Test index under file:// or local static hosting. Check sidebar, scroll state, page input, responsive view, and both downloads. Open downloaded PDFs; a print dialog or a successful build process alone is insufficient. Retain source JSON and build instructions with outputs. Deliver concise links and disclose material unverified integrations.
